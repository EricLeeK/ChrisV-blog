哈喽大家好，我是 ChrisV，这篇文章想聊聊 Skill 路由里的两个指标：精度和召回。

前段时间我读到一篇阿里写在公众号上的博客，讲他们怎么优化 AI Agent 选 Skill 的准确率，最后把首轮路由（第一次调用交给哪个 Skill）的命中率做到了 91.18%。

读完我第一反应是：这件事我年初也做过，而且最后得出的结论是「白忙活」，后来也就搁下了。

但这次回顾，我发现我和阿里这个文章其实是在修同一个系统里的两个不同指标。这篇文章打算把这件事完整复盘一遍：我当初为什么做、做到哪一步、为什么放弃，以及那篇博客让我学到了什么。

## 一、我遇到的问题：Skill 不按我想的被调用

今年年初 Skill 刚开始火的时候，我看到什么都想装。收藏夹里攒了一堆，实际用起来的没几个。ps：我一直是收藏夹战神

用起来之后问题很快就来了：想让某个 Skill 干活的时候，它不触发；不需要它的时候，它反而出来了。

最典型的一次，我写了一个做「自媒体分享卡」的 Skill，用来生成一张适合发小红书的那种图卡。每次我需要它，Agent 都会把任务派给另一个偏 PDF 处理的 Skill。我要的是图，它按文档流程走。

一开始我以为是模型能力问题。后来思考了一阵子，初步想法是，我没让它知道「什么时候该用它」。

## 二、Skill 的加载机制，决定了这是一类检索问题

这里要先解释一下 Skill 的加载机制。

现在主流的 Agent 采用渐进式披露：平时只保留一份 description（Skill 的简介，也是 Agent 决定要不要用它时唯一能看到的文字），等模型判断这次任务该用某个 Skill，才把完整内容加载进来。

这个设计很省 Token，但也带来一个直接后果：**能不能找到对的 Skill，取决于 description 和用户 prompt 对不对得上，也取决于模型有没有意识到这一点。**

问题在于，这两样东西通常不在一个语义空间里。

我的 prompt 是任务视角的：我要完成什么。description 是工具视角的：这个工具在技术上能做什么。

举个例子。我要钉钉子，需要一把锤子。但锤子的 description 只会写：一个用来敲击的手握式工具，balabala。这个描述完全正确，可模型要从「敲击」走到「钉钉子」，中间还隔着几步推理。

我当时正在研究 RAG（检索增强生成，把内容建成索引，再按语义相似度取回相关片段），就很自然地想：既然这是一种「找」的问题，那能不能用检索来解决？

把每个 Skill 的 description 建成向量索引，prompt 进来之后先检索，把最相关的几个 Skill 交给模型判断。

这个思路还有一个额外好处：省 Token。以前的做法是把所有 Skill 的 description 全部预加载进上下文，Skill 越多越贵，而且每次对话都要重来一遍；建索引只需要建一次。

当然，索引也很难只建一次，因为语义会随着时代发展漂移。比如最近听到很多「羁绊」这个词，其实原意是偏贬义，指阻碍；但现在在网络上说羁绊，基本是指人与人之间的缘分和联结。词义变了，索引也会慢慢过时。但维护一个索引，仍然比每次把全部简介重新加载一遍便宜。

于是我开始实验了。

## 三、两版实验探索

补一下背景：我先是在 HuggingFace 上找了一个 8 万个 Skill 的数据集，用来做压力测试；下面两版方案，都在这个规模上跑。

### 第一版：直接拿 description 做向量检索

第一版很朴素：description 直接向量化，prompt 进来算余弦相似度，取最相关的几个。

结果在思维跨越较大的问题上不行，检索出来的结果和答案 Skill 对不上。

原因还是那个语义错位：description 站在工具那一边，prompt 站在需求侧。

### 第二版：把「用户可能会问的话」写进 description

第二版的思路是，让模型先预判：这个 Skill 可能会被什么样的提问用到？把这些预判的提问一起写进 description，做一轮语义增强。

这个改法确实有用，尤其是在复杂任务上——那种要经过好几步推理才到达某个 Skill 的需求，命中率明显变好了。

但直白场景反而变差了。本来我一句「做个图卡」，靠功能边界就能分清，改完之后模型被噪音搞得开始分不清了。

一好一坏，加在一起，整体几乎没变化。就很鸡肋。

[![补充用户问法前后的语义关系示意：复杂请求更容易命中，简单请求更容易混淆](/images/skill-routing/semantic-enrichment.jpg)](/images/skill-routing/semantic-enrichment.jpg)

但它仍然有点好处就是 0 Token。运行的时候不需要耗费 Token 推理一步，每次直接检索能用的 Skill。

不过这个结果还是没能说服我继续往下研究，而且这个 Token 消耗量大得不可思议，8 万个 Skill 每一个进行一轮语义增强，当时我是拿小米送的 100 亿 Token 做的这个项目，好几个实验做下来几乎把 100 亿用完了，成本吃不消，这事后面就不了了之了。

## 四、阿里那篇博客，是怎么做的

那篇博客讲的是同一件事：Agent 该把活派给哪个 Skill。

他们的做法很工程化：搭一个本地回放环境，把消息历史、模型、前置工具全部冻结，只改 description，观察首轮路由会不会变。模型是真调用，但检索、目录、简介都由冻结材料提供。

每道题做 3 次，按多数结果计分，三次都不一样就算未命中。

而且他们每次改动前先写下归因假设：我猜是哪里让模型选错了；然后只改那一处，再看错例有没有修好、以及本来就能对的例子有没有出现问题。

最后的结果是，34 条开发请求命中 31 条，准确率 91.18%。很牛的一个效果啊，不过我没在文章中看到 baseline 的准确率是多少。

后面我和 DeepSeek 讨论了这个文章和我做的事情的区别，大肥鱼告诉我**我们俩做的虽然是同一件事，但优化的指标其实是不同。**

## 五、精度和召回

这里需要先把两个概念说清楚：

- **精度**：请求进来之后，在几个候选 Skill 里选对的那一个。它对应的是假阳性——本来不该用它，却用了。
- **召回**：在所有 Skill 里，把真正该用的那个找出来。它对应的是假阴性——本来该用它，却没找到。

学过概率统计的话，这对应第一类错误和第二类错误。两类错误各自独立，一类减少，另一类未必同步减少。

[![用分享卡请求区分两种路由失败：正确 Skill 未进入候选，以及进入候选后仍被选错](/images/skill-routing/recall-vs-selection.jpg)](/images/skill-routing/recall-vs-selection.jpg)

放到我们各自的方案里就清楚了：

| 维度 | 阿里博客 | 我的 skillrag |
| --- | --- | --- |
| 优化目标 | 精度 | 召回 |
| 解决什么 | 候选里选错 | 大池子里找不到 |
| 方法 | 围绕交付目的改 description，划清相邻能力边界 | 把预判的用户提问写进 description，做语义检索 |
| 适用规模 | 几十到几百个 Skill | 几千到上万个 Skill |

这两个指标可以两个都低，也可以一个高一个低，不能简单相加。

而更关键的是我后来才想明白的一点：**我做的补召回的手法，代价其实就是牺牲精度。**

为什么第二版会出现「复杂变好、直白变差」？因为我把 description 写得更像用户会问的话了，但相邻的那几个 Skill，description 也一起变得更像用户会问的话了。

判别信息被稀释了。本来「图卡」和「PDF」是两个清晰的功能边界，都朝用户提问的方向调整之后，模型反而更容易认错。

问题出在方法本身：副作用是方法自带的，调整手法消不掉。

阿里那套恰好相反：用「交付目的」给相邻 Skill 的能力划边界，方向是提高判别力，所以他们的首轮路由能提上去。他们的 Skill 库本来就少，不需要考虑召回的问题，文章里也就没有展开。

我们俩都在改 description，我为了让 RAG 更准，往「像用户提问」的方向改；他往「好区分」的方向改。方向不同，指标就不同。

## 六、另一个差别：两种「省」

阿里那套省的是**验证成本**，发生在做实验的时候：首轮路由回放只观察到第一次调用就停，不跑完整业务，所以改一次 description 的验证很快。博客里提到，两次候选生成的核心阶段都只要三分钟出头。

而我省的是**运行成本**，发生在投产之后：索引建一次，之后线上每次对话都不需要把全部 description 加载进上下文。

一个是做实验时省时间，一个是上线后省 Token。

[![Skill 路由的前期实验投入、首次选择回放验证时间与每次请求的简介 Token 成本对比](/images/skill-routing/cost-comparison.jpg)](/images/skill-routing/cost-comparison.jpg)

这也解释了为什么我们最后会走到两个方向：他们在优化「怎么更快验证一次修改」，我在优化「怎么让运行时更便宜且准确」。

## 七、所以我现在怎么看这件事

最后经过这次探索，我也确实发现，对于这类问题要先分清自己缺的是哪一半。**是「没找到」，还是「选错了」？** 没找到，就去做检索、做索引、做语义桥接；选错了，就去改 description、划边界、写清楚交付目的。并且要想清楚引入一项操作会不会带来副作用，先做可行性分析，再决定要不要动手。

另外，方法的选择取决于规模。用户池子只有几十个 Skill 的话，把能力边界写清楚、加一套回放验证，完全就够了，上 RAG 属于过度工程；池子到了几千上万，检索才值得考虑。但说实话，目前我真没刷到过谁的单人 Skill 数量超过 1000 个（除了收藏夹战神）。大家往往前期加了一堆 Skill，发现自己很少用，还影响模型推理质量和成本，后来就删了。至少我是这样，现在越来越想删掉各种加的古早 Skill，比如什么头脑风暴、各种代码规范类的等等。

## 八、Skill 会消失吗

现在模型能力越来越强，我最近在想一个问题：Skill 这个形态未来会不会消失。我现在的想法是，它不会消失，但会越来越少。因为很多 Skill 的能力正在被内化到模型里。

之前很多 Skill，是在教模型在一个泛场景下怎么做更好——预设一些好例子，给一些规范，比如 UI/UX 设计相关的 Skill，还有现在比较火的、让 Opus 5.5 用代码做视频的 Skill。这类 Skill 我觉得会逐渐消亡，特别是模型攻破越来越多领域之后，模型在这些领域不需要人的指导了，人类纯属帮倒忙。但这类 Skill 也不会归零，它会慢慢变成让模型和人类对齐的工具：模型能力可能很高，但在一个领域的努力方向或者品味和人类不同，或者只是和你想要的 vibe 不同，就可以用一个 Skill 去对齐。所以这种 Skill 会一直活下去。

还有一些 Skill 也不会消失，其实也能归到刚刚说的这一类：每个人独特工作流的 Skill。有人习惯在做一件事的时候走一套独特的路线，这导致了他产出内容的差异化。这种有点像做得比较好的智能体记忆，搭配一个复盘自进化 Skill。可能之后这种能力再次内化到模型中之后，你只要做一遍它就记住了，不需要再单独写一个 Skill；包括前面的品味，也可能在和 Agent 的相处中，它就慢慢学会了偏好。不过这时候 Skill 的作用在于一种分发：品味的分发，或者独特工作流的分发。比如你觉得别人的品味很好，你不想待在自己的茧房里，就把一个你欣赏的人的品味 Skill 拿来给 Agent 装上，然后你的 Agent 就开始给你推送他的品味的内容。

总之，我认为 Skill 在未来会越来越少，但这种渐进式披露的思想，应该会一直流转在 Agent 的架构设计之中。

## 写在最后

读完那篇阿里博客，我把几个月前那个「白忙活」的结论重新复盘了一遍：召回和精度有可能相悖，一个提高，另一个未必同步提高。

当然，知道两者会互相牵制，和真的把两端都兼顾好，中间还有很长的路。无限进步吧！
