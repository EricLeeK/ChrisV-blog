# 项目介绍营销化改写设计

## 目标

将博客中 9 个项目页面从“一句话概括”升级为面向潜在使用者的完整介绍。文案必须建立在 GitHub 仓库实际代码、功能入口、数据流和实验内容之上，不能只依据项目名称或 README，也不能把研究原型描述成已经成熟交付的商业产品。

## 文案策略

整体语气采用“克制可信”，再根据项目类型调整营销强度：

- 应用型项目：GrsAI Studio、ToonVocab、Nihongo Study TutorWeb、V-Life。优先从用户痛点和使用结果切入，突出具体功能、体验收益和适用场景。
- 开发者工具：SuperTT Skills、SynCRAG Skill。突出工作流效率、集成方式、技术差异和能够帮助开发者解决的问题。
- 科研项目：Auto-opt-PINN、ST-PINN、JAX-FEM4Geo。突出研究问题、方法设计、实验基础、可复现价值和对研究者的启发，明确其研究原型属性。

## 页面结构

每个项目页面正文控制在约 500–900 个汉字，根据项目复杂度自然调整，不机械套用标题。内容应覆盖：

1. 项目的核心价值和目标用户。
2. 用户或研究者当前面对的具体问题。
3. 项目采用的解决方式。
4. 从代码中确认的核心能力与使用流程。
5. 项目的差异化价值、适用场景和启发。
6. 对成熟度、依赖条件或研究边界的可信说明。

列表页和详情页头部使用的 `description` 同步改写为更有吸引力的短摘要，但保持适合卡片展示的长度。详情正文使用 Markdown 小标题和列表提升可读性。

## 事实边界

- 只描述仓库当前 `main` 分支中能够找到代码或实验材料支持的能力。
- 不使用“行业领先”“彻底解决”“生产级”等无法验证的绝对化表达。
- 有公开评测数字时可以引用，但必须明确评测对象和条件。
- 尚未形成完整产品体验的科研项目，以“研究框架”“实验平台”“探索”表述。
- 外部 API、模型密钥、Supabase、微信公众号等依赖必须如实说明。

## 验收标准

- 9 个 `src/content/projects/*.md` 文件的 `description` 和正文全部完成替换。
- 应用项目明显更面向用户和结果，科研项目保持专业、可信。
- 每项关键能力都能在对应仓库代码、配置、测试或实验脚本中找到依据。
- 中文表达自然，技术名词和中英文空格符合统一规范。
- `npm run build` 成功生成全部项目详情页。
